  事実関係

  hakoniwa.c は「ゲーム専用ファイル」ではなく「全部入りの単一ファイル」です。
  意図的な設計で、ゲームロジックだけでなく、X11/Win32/Cocoaのウィンドウ層・音声
  層まで全4,162行を1ファイルに収めています（冒頭コメントに「PoCのgui_window_v6.c
  を土台に構築」と明記。hakoniwa.c:1-11、game/REPORT-v0.md:4-5）。つまり「共通部
  分」という別ファイルはそもそも存在せず、ファイル内のセクション分けで代替してい
  る構造です。

  そして問題の送信処理 net_send_all は、そのファイル内では既に共通ヘルパのセクシ
  ョン（hakoniwa.c:545、コメントも「shared with X11」）に置かれています。関数自
  体はfd汎用ですが、実際に使っているのはX11の16箇所のみで、音声は生の write()
  を直接使っています。

  本当の問題は「コピーによる重複」

  同一のバグ持ちコードが2箇所にあります:

  - game/src/hakoniwa.c:547 の net_send_all
  - samples/ape-poc/src/gui_window_v6.c:384 の net_send_all —
  diffで完全一致のコピー。v6も同じ条件（O_NONBLOCK設定あり:
  v6.c:2400）でバグが発現します

  さらにコピーの過程で、O_NONBLOCKにする理由のコメント（v6には「polling用」とあ
  った）がhakoniwa.c側では落ちています。O_NONBLOCKは受信ポーリングのために設定さ
  れており、送信側への影響が考慮されていなかった、というのがバグの経緯です。

  見解

  - ファイル分割は今すぐは不要と考えます。単一ファイルは1.44MBコンテスト規模では
  管理コストが低く、分割はビルド構成の変更を伴います。分けるなら「プラットフォー
  ム層をゲームと分ける」観点より「PoCと本体で同じコードを二重管理しない」観点が
  本質ですが、samples/ape-poc
  は歴史的記録（PoC）であり今後更新しない前提なら、重複は凍結扱いで許容できます
  - 直すべきはバグ本体: hakoniwa.c の net_send_all にEAGAIN時の poll+再送を入れ
  る（数行の修正）。PoC側は記録なので直さなくてよい、が私の判断です

  この方針（hakoniwa.cのみ修正、ファイル分割なし）でよければ、実装エージェントに
  修正させて verify-ai.sh の回避策なし動作まで確認させます。
